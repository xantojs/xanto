# Xanto.JS — File-based Routing Syntax

## 1. Корневой маршрут и папки (сегменты пути)

Все маршруты строятся относительно корневой директории роутинга (например, `routes/` или `api/`).

| Синтаксис      | Пример          | Значение                                                                 |
| -------------- | --------------- | ------------------------------------------------------------------------ |
| `/`            | `routes/`       | Корневой уровень приложения (`/`)                                        |
| `folder/`      | `users/`        | Статичный сегмент пути                                                   |
| `[name]`       | `[id]/`         | Динамический сегмент (строковый по умолчанию)                            |
| `[name::type]` | `[id::number]/` | Типизированный динамический сегмент (`number`, `uuid`, `boolean` и т.д.) |
| `[...name]`    | `[...slug]/`    | Именованный catch-all сегмент (жадный матчинг остатка пути)              |
| `(name)`       | `(admin)/`      | Группа маршрутов — чисто логическая, не влияет на итоговый URL           |
| `_name/`       | `_helpers/`     | Приватная папка — полностью игнорируется роутером                        |

### Ограничения по структуре папок:

- **Терминальность catch-all:** сегмент `[...name]` может быть только **последним** (терминальным) сегментом в цепочке пути. Вложенные папки внутри catch-all сегмента запрещены и вызывают ошибку сборки.
- **Типизация catch-all:** модификатор `[...name::type]` **не поддерживается** (catch-all всегда захватывает сырой массив строк/остаток пути).

## 2. Файлы методов

| Синтаксис            | Пример                                                 | Соответствие URL            |
| -------------------- | ------------------------------------------------------ | --------------------------- |
| `{method}.ts`        | `get.ts`, `post.ts`, `put.ts`, `delete.ts`, `patch.ts` | Метод для текущего сегмента |
| `{name}.{method}.ts` | `user.get.ts`, `create-user.post.ts`                   | Метод для текущего сегмента |

- `{name}` — произвольный префикс для удобства разработчика (улучшает поиск по файлам в IDE). Фреймворком полностью игнорируется при построении маршрута.
- **Корневой URL (`/`):** обрабатывается файлами методов, лежащими непосредственно в корневой папке роутинга (например, `routes/get.ts` или `routes/index.get.ts`).

---

## 3. Специальные и служебные файлы

| Синтаксис              | Пример                | Назначение                                           |
| ---------------------- | --------------------- | ---------------------------------------------------- |
| `middleware.ts`        | `middleware.ts`       | Middleware для текущей папки и всех вложенных        |
| `{name}.middleware.ts` | `auth.middleware.ts`  | То же самое, `{name}` игнорируется фреймворком       |
| `error.ts`             | `error.ts`            | Обработчик ошибок для текущей папки и всех вложенных |
| `{name}.error.ts`      | `validation.error.ts` | То же самое, `{name}` игнорируется фреймворком       |

### Игнорируемые (приватные) файлы:

Файл считается **игнорируемым (приватным)**, если его имя не соответствует ни одному из шаблонов:

- `{method}.ts` или `{name}.{method}.ts`
- `middleware.ts` или `{name}.middleware.ts`
- `error.ts` или `{name}.error.ts`

Примеры игнорируемых файлов: `service.ts`, `types.ts`, `schema.validator.ts`.

### Ограничения и порядок выполнения:

- **Один файл на уровень:** в одной папке допускается только один middleware-файл и только один error-файл (независимо от `{name}`-префикса). Два файла с суффиксом `.middleware.ts` (например, `auth.middleware.ts` + `log.middleware.ts`) в одной папке — **ошибка сборки**.
- **Каскад Middleware (Top-Down):** цепочка middleware выполняется сверху вниз (от корня `routes/` к целевому эндпоинту).
- **Каскад Error Handlers (Bubble-Up):** перехват ошибок идёт снизу вверх (ошибку ловит ближайший родительский `error.ts` в дереве).

## 4. Символы и модификаторы

| Символ | Место                          | Значение                                             |
| ------ | ------------------------------ | ---------------------------------------------------- |
| `[ ]`  | Вокруг имени сегмента          | Динамический параметр (`[id]`)                       |
| `::`   | Внутри `[ ]`                   | Разделитель имени и типа параметра (`[id::number]`)  |
| `...`  | Внутри `[ ]`, перед именем     | Catch-all модификатор (`[...slug]`)                  |
| `( )`  | Вокруг имени папки             | Группа без влияния на URL (`(admin)`)                |
| `_`    | В начале имени папки           | Приватная папка, игнорируется роутером (`_helpers/`) |
| `.`    | Между именем и методом в файле | Разделитель `{name}.{method}.ts`                     |

---

## 5. Приоритет матчинга (от высшего к низшему)

Если входящий URL может совпасть с несколькими маршрутами на одном уровне дерева, проверка выполняется в строгом порядке:

1. **Статичный сегмент** (`/users/settings`)
2. **Типизированный динамический сегмент** (`/users/[id::number]`)
   - _Если значение не прошло валидацию типа, роутер переходит к следующему правилу в списке приоритетов (fallback)._
3. **Обычный динамический сегмент** (`/users/[id]`)
4. **Catch-all сегмент** (`/users/[...slug]`)

> **Примечание:** Разрешается сосуществование сегментов **разных уровней приоритета** в одной родительской папке (например, `users/settings/`, `users/[id::number]/` и `users/[...slug]/`). Роутер автоматически выстроит их в каскад согласно приоритетам.

---

## 6. Конфликты — все считаются ошибкой сборки

Любая неоднозначность в маршрутах отлавливается на этапе статического анализа дерева:

- **Дублирование методов:** два файла на один HTTP-метод в одной папке (`get.ts` + `user.get.ts`).
- **Коллизии одного уровня приоритета:**
  - Два разных обычных динамических сегмента на одном уровне (`[id]` и `[slug]`).
  - Два разных типизированных сегмента на одном уровне (`[id::number]` и `[slug::string]`).
- **Коллизии через группы `(group)`:** два одинаковых результирующих URL из разных групп (например, `(auth)/login/get.ts` и `(public)/login/get.ts`).
- **Дублирование имён параметров в пути:** одинаковое имя параметра дважды в одном пути (например, `[id]/posts/[id]`).
- **Нетерминальный catch-all:** папка внутри catch-all сегмента (`[...slug]/subfolder/`).
- **Неоднозначный trailing slash:** `/users` и `/users/` регистрируются как один и тот же маршрут; попытка разделить их поведение — ошибка.

---

## 7. Регистр имён

- Все URL-пути приводятся фреймворком к нижнему регистру (`lowercase`) автоматически при построении дерева маршрутов.
- **Ограничение:** на регистронезависимых файловых системах (Windows / macOS) файлы, отличающиеся только регистром (например, `User.get.ts` и `user.get.ts`), физически конфликтуют на диске ещё до сканирования фреймворком.

---

## 8. Отклонённые варианты (сознательно не поддерживаются в v1)

- Опциональные сегменты `[[name]]`
- Несколько параметров в одном сегменте пути (`[width]x[height]`)
- Безымянный catch-all `[...]`
- Типизированный catch-all `[...slug::type]`
- Environment-суффиксы файлов (`.dev.ts` / `.prod.ts`)

**Причина отказа:** однозначность статического анализа, детерминированный матчинг без накладных расходов и простота архитектуры для v1.
